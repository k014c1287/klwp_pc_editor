# モジュール設計の哲学

この文書は、KLWP Desktop Editorを拡張・保守するときの判断基準を定めるものです。個別のクラス構成や処理順は `KLWPエディタ_設計仕様.md`、利用方法はルートの `README.md`、実データの根拠は `sample/` を参照します。

ここでいう「モジュール」は、Pythonの責務単位とKLWPの要素（Module）の両方を含みます。どちらについても、局所的に便利な実装より、成果物全体の互換性と利用者の編集体験を優先します。

## 1. 目指すもの

このプロジェクトの目的は、KLWPをPC上で完全に模倣することではありません。実際のKLWP成果物を壊さずに読み書きし、Androidへ持ち込む前に、できるだけ正確かつ直感的に編集・確認できる道具を作ることです。

そのため、次の三点を同時に満たすことを目標にします。

1. KLWPが読み込める互換性のある成果物を生成する
2. 既存プリセットの未知設定を失わずに往復保存する
3. PC上での編集操作を理解しやすく、速く、取り消し可能にする

## 2. 正解は実データにある

仕様の優先順位は次のとおりです。

1. `sample/` の実成果物とKLWP実機の表示・挙動
2. KLWPで保存し直した成果物の構造と、Androidへの往復結果
3. 実データから固定した回帰テストと画像差分
4. 現行の設計資料とコード
5. 名前や一般的なUI慣習からの推測

上位の根拠と下位の記述が矛盾した場合は、下位を直します。既存実装に合わせてsampleを変更したり、推測を正当化するために実データを無視したりしません。

発見したKLWP仕様は、まず最小のsampleまたは回帰テストで再現し、その後に実装と設計資料へ反映します。

## 3. KLWPの意味を別の都合へ置き換えない

画面上で位置がX/Y座標に見えても、KLWPがアンカーからのオフセットや四辺余白として保存するなら、その意味モデルを維持します。同様に、ページ数、Global、Kode数式、アニメーション、タッチイベント、レイヤー内の並び順も、エディタ独自の簡略モデルへ不可逆に変換しません。

UIはKLWPの内部表現をそのまま露出する必要はありません。日本語のアンカープルダウン、カラーピッカー、直接リサイズなど、利用者に理解しやすい表現へ翻訳します。ただし、保存時にはKLWP本来の意味へ確実に戻せることを条件とします。

## 4. 未知の情報を壊さない

このエディタが理解していないキー、将来バージョンの設定、複雑なKode式も、編集対象でなければそのまま保持します。

- 辞書全体を既知スキーマへ作り直さず、変更対象のキーだけを書き換える
- 画像・フォント・その他ZIPエントリーを、必要なく削除・改名しない
- 形式移行が必要な場合は、参照元と参照先を同時に更新する
- 近似表示できない設定を「存在しない設定」として扱わない

新規作成の正しさだけでなく、読込→保存→再読込で情報が残ることを互換性の中心に置きます。

## 5. 永続状態と編集状態を混ぜない

`.klwp` に保存される状態と、PCエディタだけで使う状態を明確に分けます。

- プリセット、モジュール、Global、数式、ページ数は成果物の状態
- 選択、ズーム、パン、一時ガイド、キャッシュ、操作中の補間値は編集・プレビュー状態
- プレビュー用の日時、天気、電池、音楽などの模擬値は成果物へ混入させない
- UIの都合で追加した状態は、保存形式へ書き出す前に境界で止める

この境界を維持するため、アプリケーション状態は `ApplicationMemory` に集約し、KLWPアーカイブとは別に管理します。

## 6. 操作は直接的で、可逆であること

利用者が画面上で行った操作は、見た目と保存結果が一致するようにします。

- ドラッグした方向へ要素が動く
- 画像は縦横比を保ち、図形は必要に応じて自由に変形できる
- 複数選択では同じ操作を選択対象全体へ適用する
- 左の要素ツリーを選択元とし、プレビュー上の偶発クリックで選択を奪わない
- 入力欄のキー操作と要素操作を競合させない

破壊的な操作を確認ダイアログだけで防ぐのではなく、Undo/Redoで確実に戻せる設計を優先します。削除、移動、サイズ変更、設定変更は、意味のある一操作単位で履歴へ記録します。

## 7. 操作中の速さと確定後の品質を分ける

連続入力のたびに高コストな全体処理を行うと、正確でも操作しづらい道具になります。操作の追従と最終品質を二段階に分けます。

- ドラッグやホイールの入力中は、既存描画や局所更新を使って即座に追従する
- 入力停止またはリリース時に、スナップ補正や高品質な全体描画を一度だけ行う
- 構造が変わらない操作では、要素ツリーなど無関係なUIを再構築しない
- キャッシュは成果物の正しさを変えず、いつでも再生成できるものに限定する

体感速度の改善によって保存値や最終描画の精度を落としてはいけません。

## 8. 小さな責務を組み合わせる

巨大な実行ファイルへ機能を積み重ねず、アーカイブ、描画、配置、プレビュー、UI、操作、検証を別の責務として分離します。

- クラスとメソッドは小さく保ち、名前で意図を説明する
- ドメインの値は値オブジェクト、複数対象はファーストクラスコレクションで扱う
- 生のプリミティブ値はTkinter、Pillow、JSON、ZIPなど外部境界で展開する
- 深い条件分岐より、早期return、ディスパッチ、協調オブジェクトを使う
- 状態を隠すGetter/Setterの増殖ではなく、意味のある操作を公開する

Object Calisthenicsの規約は目的ではなく、責務の混在や変更影響の拡大を早期に発見するための制約として使います。

## 9. 近似は明示し、外部世界を勝手に実行しない

PillowによるPCプレビューはAndroidの描画エンジンそのものではありません。Skia固有の画素差、未対応Kode関数、新しいShader、端末固有データには限界があります。

- 対応済み、近似、未対応を文書とUIで区別する
- 近似できない構文も保存時には保持する
- アプリ起動、音楽操作、Intentなどは設定できても、PC上で無断実行しない
- スマートフォンのアプリ一覧など取得できない外部情報は、手入力や将来拡張の境界として扱う

「表示できない」と「保存できない」を混同しません。

## 10. 検証は層を重ねる

一種類のテストだけで正しさを判断しません。

1. 値オブジェクトや計算の単体テスト
2. load→save→loadの往復テスト
3. 複数KLWPバージョンと実成果物の回帰テスト
4. ヘッドレス描画と実機スクリーンショットの画像差分
5. AndroidのKLWPでの最終読込・表示確認

不具合修正では、可能な限り先に再現条件をテストへ固定します。数値が合うだけでなく、アンカー、階層、画像比率、選択状態など、問題を生んだ意味の境界を検証します。

## 11. 文書と変更履歴を製品の一部として扱う

文書の役割を分けます。

| 場所 | 役割 |
| --- | --- |
| `README.md` | 利用者向けの導入、操作方法、開発入口 |
| `doc/KLWPエディタ_設計仕様.md` | 現在の構造、データ契約、処理順、互換性、検証方法 |
| `doc/モジュール設計の哲学.md` | 実装判断が割れたときの優先原則 |
| `doc/商用ツール比較_UX改善課題.md` | 外部評価として受領したUX課題の原文 |
| `doc/TODO_UXフィードバック対応.md` | 指摘の妥当性、採否、PR境界、対応状況 |
| `sample/` | 仕様判断と回帰検証の一次資料 |

特定の支援ツールや担当者だけを前提にした引継ぎ資料は作りません。実装、テスト、設計資料は同じ変更単位で更新し、レビュー可能なブランチとPRにまとめます。

## 12. 迷ったときの確認事項

新しい実装案は、少なくとも次を確認します。

- sampleまたは実機の根拠があるか
- 未知キーや既存アセットを失わないか
- KLWP本来の保存意味を保っているか
- 一時的なUI状態を成果物へ混ぜていないか
- 操作結果をUndoで戻せるか
- 文字入力や別操作のショートカットを奪わないか
- 連続操作中に不要な全体再描画・再構築をしていないか
- 近似や未対応を利用者へ誤認させないか
- 単体、往復、描画、実機のどの層で検証するか明確か
- コード、テスト、設計資料が同じ仕様を説明しているか

判断が割れる場合は、「より多く自動化できる案」よりも「実成果物を壊さず、利用者が結果を予測でき、後から戻せる案」を優先します。
